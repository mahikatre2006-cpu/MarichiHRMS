# MarichiHR HRMS — Role-Based Access Control (RBAC) & 5-Level Scoping Architecture

This document describes the authorization, permission matrix, and dynamic data scoping model in **MarichiHR HRMS Phase 1**.

---

## 1. Five-Level Scoping Hierarchy

Data visibility and mutation access in MarichiHR follow a strict hierarchical scoping model:

```text
       ┌────────────────────────┐
       │   1. ORGANISATION      │  Global visibility across all entities & departments
       └───────────┬────────────┘
                   │
       ┌───────────▼────────────┐
       │      2. ENTITY         │  Restricted to user's assigned legal entity (e.g., India Pvt Ltd)
       └───────────┬────────────┘
                   │
       ┌───────────▼────────────┐
       │   3. DEPARTMENT        │  Restricted to user's department (e.g., Engineering)
       └───────────┬────────────┘
                   │
       ┌───────────▼────────────┐
       │      4. TEAM           │  Direct and indirect hierarchy reports (BFS tree traversal)
       └───────────┬────────────┘
                   │
       ┌───────────▼────────────┐
       │      5. SELF           │  Strictly restricted to own employee record & actions
       └────────────────────────┘
```

---

## 2. Scoping Engine (`buildScopeFilter`)

Authorization is enforced at both the route middleware layer (`authorize(permission, options)`) and the query filter layer (`buildScopeFilter(req, options)`).

### Breadth-First Search (BFS) for TEAM Scope
When an actor with `TEAM` scope accesses a resource:
1. The scoping engine queries the `Employee` collection starting from the actor's `employeeId`.
2. It iteratively traverses all direct reports (`managerId == currentEmployeeId`).
3. It recursively collects all indirect downstream reports across any depth of management tree.
4. It compiles an `$in` query filter targeting the actor's employee ID and all report IDs:
   ```javascript
   { [employeeField]: { $in: [actorEmployeeId, ...allReportEmployeeIds] } }
   ```

### Tenant Isolation Enforcement
Every query generated by `buildScopeFilter` is automatically anchored to the actor's verified `req.tenantId`:
```javascript
{ tenantId: req.tenantId, ...scopeConstraints }
```
Any client attempting to tamper with or supply a foreign `tenantId` in request bodies, query parameters, or URL paths is immediately rejected with a `403 Forbidden` error.

## 4. Hardened Security & Anti-Abuse Rules

1. **Self-Approval Prevention**:
   - Managers or HR Admins who submit leave requests or attendance regularisations are strictly forbidden from approving their own submissions (`ForbiddenError: Self-approval violation: Employees cannot approve their own requests`).
   - Requests must be routed to their designated manager or a `SYSTEM_ADMIN`.

2. **Attendance Lock Guard**:
   - Once an attendance period is locked (`status: 'LOCKED'`), all mutation attempts for dates within that period are rejected with `422 Unprocessable Entity`.
   - Blocked paths: `punchIn`, `punchOut`, `submitRegularisation`, `approveRegularisation`, and `overrideAttendance`.

3. **Audit Log Immutability**:
   - All audit logs written to MongoDB are protected by Mongoose pre-hooks on `updateOne`, `updateMany`, `findOneAndUpdate`, `deleteOne`, `deleteMany`, and `findOneAndDelete`.
   - Any programmatic attempt to alter or delete an audit record throws a fatal runtime exception.

4. **Double-Entry Leave Ledger Immutability**:
   - The leave balance ledger is strictly append-only.
   - Adjustments, accruals, deductions, and cancellations are recorded as separate balanced ledger entries. Direct mutation or deletion of ledger rows is prohibited.

5. **Approval Delegation Engine**:
   - Out-of-office managers can create time-bound `LeaveApprovalDelegation` records specifying a delegatee employee.
   - The RBAC `isEmployeeInTeam` scoping engine automatically checks active delegations for the delegating manager, allowing the delegatee to approve team leave requests with `TEAM` scope during the active delegation window.

6. **Blackout Period Protection**:
   - Leave requests falling within an active `LeaveBlackout` period are blocked with `409 Conflict`.
   - Only actors with `LEAVE_BLACKOUT_MANAGE` (HR Admin / System Admin) can override and approve leaves during blackout periods.

7. **RFC 6819 Token Family Revocation & Session Invalidation**:
   - Refresh tokens are single-use and rotated on every `/api/v1/auth/refresh` request.
   - If a previously rotated refresh token is presented again (theft/replay), the reuse detection engine immediately marks all active sessions for the user as revoked and increments `user.sessionVersion`.
   - All issued access tokens with the previous `sessionVersion` are invalidated across all devices immediately.
